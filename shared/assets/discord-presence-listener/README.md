# Discord Presence Listener

Lightweight Node listener that subscribes to a Discord user's presence stream via the public [Lanyard](https://github.com/Phineas/lanyard) WebSocket relay and writes structured session events to Supabase. Originally built for NAISC Ripple as the "Discord context source" — captured what game / app the user was in to correlate with wellness signals (the R043 "late-night phone → next-day sleep drop" rule was the prime use case).

## Architecture

```
Lanyard WSS  →  listener.mjs  →  Supabase
(public relay)   (Node, long-       (3 tables + 1 view)
                  lived process)
```

**Supabase schema** (from memory — verify in dashboard before reuse):
- `discord_user_link` — maps Discord user_id ↔ app user
- `discord_presence_events` — raw event stream (every presence update)
- `discord_sessions` — derived/aggregated session records (start, end, primary activity)
- One view — name not recorded; query Supabase dashboard to recover

If the original SQL migration in the source-of-truth directory is gone, infer schema from `listener.mjs.snapshot` insert/upsert calls.

## When to reuse

- Any project that needs a **lightweight Discord presence data stream** without setting up a custom bot (no Developer Portal, no GUILD_PRESENCES intent, no token rotation)
- MVP / hackathon stage projects where Lanyard's public service is acceptable
- As reference for the general pattern: third-party relay → long-lived Node listener → structured store

## Known trade-offs

- **Third-party uptime risk** — Lanyard is a community service; no SLA. For production / paid product, swap to self-hosted bot (the listener interface stays the same — only the WebSocket source changes).
- **5–15s end-to-end latency** — Discord client polls local processes on an interval; that's the floor, not the listener's fault.
- **No history from Discord** — server-side Discord returns "right now only". Any time-series ("user spent N hours in Apex last week") must be accumulated by the listener from the moment it starts. Treat this asset as the data-accumulation layer, not a query layer.
- **Mac Mini reboot loses the process** — original deploy was nohup-detached, no launchd plist. Plist was on the NAISC "drop after 5/22" list. If reusing in production, add launchd / systemd / docker restart policy first.
