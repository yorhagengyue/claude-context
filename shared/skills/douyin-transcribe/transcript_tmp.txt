如果你現在還在花大量時間研究skill.md該怎麼排版
那你很可能已經在一個快過時的問題上越捲越深了
Google Cloud Tech轉的這篇文章
表面上是在講五種agent skill設計模式
但它最值得先聽懂的一句話
其實不是任何一個模式名
而是格式問題已經差不多結束了
作者說得很直接
現在已經有30多個agent工具
在共用同一套skill.md規格
像cloud code, Germanize, CLI cursor這些工具
外層長得越來越像
也就是說你再去糾結VAML怎麼寫
目錄怎麼擺, references和assets怎麼命名
這些事情已經不再是分水嶺了
真正的分水嶺變成什麼?
是內容設計
也就是同樣一個skill.md外殼
裡面到底放什麼邏輯,用什麼資源
怎麼讓模型只在需要的時候加載對的內容
作者舉了一個很典型的例子
一個將模型寫fast API的skill
和一個四步走的文檔流水線skill
外面看都長得差不多
但裡面的設計完全不是一回事
一個更像知識封裝
一個更像流程控制
問題根本不再格式
而在內容結構
接著文章先回顧了
Google ADK的skill toolset三層結構
第一層是list skills
只給模型看到skill名字和description
第二層是load skill
模型需要的時候再把完整指令拿進來
第三層是load skill resource
只有真正要讀參考文檔
模板或資源文件時才去按虛加載
這個設計背後的核心邏輯很重要
叫progressive disclosure
也就是漸進式披露
先給少量信息
讓模型自己決定
什麼時候再往下拿更多內容
作者甚至直接給了一個量化判斷
每個skill在啟動時
大概只多帶來100個choken左右的描述成本
真正中的部分
不應該一開始就全部塞進上下文
而是按虛再讀
你看到這裡就會明白
skill設計的關鍵
從來不是把所有規則一口氣塞滿
而是先把入口做清楚
讓模型能找到它
再在需要時拿到更深的內容
所以文章一上來
就先拋出兩個最常用
也最容易上手的模式
第一個叫to wrapper
它本質上是給某個酷
某個框架
某個內部系統封一個即時專家包
比如 fast api terraform
數據庫查詢規範
安全策略
這些東西模型不是完全不會
但你希望它在處理這個領域問題時
穩定遵守你團隊的那套規則
你就把這些規範放進references裡
讓skill在需要時加載
這個模式最值錢的地方
是把專家經驗從系統提示詞裡拆出來
變成按虛調用的知識包
第二個叫generator
這個模式不是讓模型變專家
而是讓模型穩定產出固定結構的東西
比如技術報告
API文檔
commit message
或者你們團隊自己的agent scaffold
它通常會同時用到assets和references
assets裡放模板
references裡放風格規則
skill自己負責把流程串起來
先加載規則
再加載模板
再補齊缺的信息
最後按固定格式to結果
你會發現它和to wrapper的差別很大
前者解決的是按什麼規則做
後者解決的是按什麼結構產出
所以第一集真正要記住的結論只有一個
現在做skill
別再把精力放在格式上了
真正拉開差距的
是你能不能先判斷這個skill到底是在封裝知識
還是在穩定產出
如果這一步都沒想清楚
你後面寫的再規範
也大概率只是一個看起來很標準的功課

因為從第三個開始
Google講的已經不是怎麼給模型補知識了
而是怎麼讓模型按標準審查
先問再做
甚至被強制卡在一個不能亂挑佈的流程裡
得音
